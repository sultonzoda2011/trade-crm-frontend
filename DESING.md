# TradeCRM — Design System & UI Guidelines

> **Назначение:** единый источник правил визуального оформления TradeCRM для разработчиков и AI-агентов. Перед созданием или изменением UI сначала изучайте этот документ и переиспользуйте существующие компоненты.
>
> **Область действия:** frontend `sultonzoda2011/trade-crm-frontend`. Дизайн-токены находятся преимущественно в `app/styles/global.css`, UI-примитивы — в `app/components/ui/`, общие компоненты приложения — в `app/components/shared/` и `app/components/layout/`.
>
> **Последняя редакция:** 2026-10-18.

## 1. Визуальная концепция

TradeCRM — профессиональная CRM для торговых предприятий с **mobile-first интерфейсом, минималистичной компоновкой и визуальным языком, вдохновлённым iOS**.

Ключевые принципы:

1. **Сначала ясность, затем декор.** Суммы, задолженности, остатки, статусы и главные действия должны считываться раньше второстепенной информации.
2. **Спокойные поверхности.** Используйте нейтральный фон, карточки и мягкое разделение групп вместо тяжёлых рамок и многочисленных теней.
3. **Синий — основной акцент.** Сохраняйте его для главных действий, активной навигации, фокуса и информационных акцентов.
4. **Семантические цвета имеют значение.** Зелёный обозначает положительное состояние, оранжевый — предупреждение, красный — ошибку, критичное состояние или опасное действие.
5. **Адаптируйте интерфейс под устройство.** Мобильный экран не должен быть просто сжатой десктопной страницей.
6. **Единообразие важнее локального эксперимента.** Сначала ищите подходящий общий компонент; не создавайте новую визуальную вариацию без реальной необходимости.

Стиль можно кратко описать как **Modern CRM + iOS-inspired UI + restrained Liquid Glass**. Стеклянные эффекты — акцент, а не базовый стиль каждой карточки.

## 2. Цветовые токены

Используйте CSS variables и семантические Tailwind-классы. Не задавайте произвольные hex-цвета внутри страниц, если подходящий токен уже существует.

### 2.1 Светлая тема

| Токен / назначение | Значение |
| --- | --- |
| `--background` — фон приложения | `#F2F2F7` |
| `--foreground` — основной текст | `#000000` |
| `--card`, `--popover`, `--elevated` — поверхности | `#FFFFFF` |
| `--primary` — основной акцент | `#007AFF` |
| `--muted-foreground` — вторичный текст | `#6C6C70` |
| `--success` — положительное состояние | `#2A9D4B` |
| `--warning` — предупреждение | `#D17800` |
| `--destructive` — ошибка / опасное действие | `#FF3B30` |
| `--chart-5` — нейтральная серия графика | `#8E8E93` |

Вторичные поверхности, поля ввода и границы основаны на полупрозрачных нейтральных системных цветах. Не заменяйте их сплошными случайными оттенками серого.

### 2.2 Тёмная тема

| Токен / назначение | Значение |
| --- | --- |
| `--background` — фон приложения | `#000000` |
| `--foreground` — основной текст | `#FFFFFF` |
| `--card`, `--sidebar` — основные поверхности | `#1C1C1E` |
| `--popover`, `--elevated` — поднятые поверхности | `#2C2C2E` |
| `--primary` — основной акцент | `#0A84FF` |
| `--muted-foreground` — вторичный текст | `#98989F` |
| `--success` | `#30D158` |
| `--warning` | `#FF9F0A` |
| `--destructive` | `#FF453A` |

Тёмная тема должна оставаться полноценной темой, а не автоматической инверсией светлой. Для компонентов используйте семантические классы, которые подхватывают текущие значения токенов.

### 2.3 Рекомендуемые семантические классы

- Фон / поверхность: `bg-background`, `bg-card`, `bg-muted`, `bg-popover`.
- Текст: `text-foreground`, `text-muted-foreground`, `text-primary`.
- Статусы: `text-success`, `text-warning`, `text-destructive`.
- Мягкие заливки статусов: `bg-success/10`, `bg-warning/10`, `bg-destructive/10`, `bg-primary/10`.
- Рамка и фокус: `border-border`, `ring-ring`.

Новые семантические цвета добавляйте централизованно в `app/styles/global.css`, включая значения обеих тем, а не определяйте отдельно в каждом компоненте.

## 3. Типографика

**Основная гарнитура: Inter Variable.** Заголовки и основной текст используют одну гарнитуру. Не добавляйте Geist, Manrope или другой шрифт без осознанного изменения дизайн-системы.

### Правила типографики

- Заголовок страницы создавайте через общий `PageHeader`, когда его API подходит задаче.
- Соблюдайте явную иерархию: заголовок страницы → заголовок секции → название записи → описание и метаданные.
- Вспомогательные подписи должны быть визуально слабее основного текста, но оставаться читаемыми.
- Для денежных сумм, количеств и других чисел используйте `tabular-nums`, чтобы цифры в колонках не смещались по ширине.
- Используйте существующие форматтеры проекта для денег и дат; не вводите отдельное форматирование только ради одного компонента.
- Помните, что типографическая шкала в `global.css` адаптируется: на мобильном базовый текст крупнее, а на десктопе таблицы используют более плотную шкалу.

Цвет не должен быть единственным способом передачи смысла: рядом с цветным индикатором показывайте подпись, число или понятную иконку.

## 4. Радиусы, интервалы и поверхности

### Радиусы

Существующие компоненты используют согласованную, но не абсолютно одинаковую шкалу:

- **Карточки и панели:** обычно `rounded-2xl` (16 px).
- **Кнопки:** обычно `rounded-xl` (12 px), если выбранный вариант компонента не задаёт другое.
- **Поля ввода:** около 10 px.
- **Плавающая навигация и glass-контролы:** круглые формы / капсулы.
- **Небольшие бейджи:** компактное скругление, соответствующее их компоненту.

Не делайте все элементы одинаково круглыми. Радиус помогает отличать карточку, интерактивный контрол и статусный бейдж.

### Отступы и плотность

Используйте стандартную шкалу spacing в Tailwind и существующие паттерны компонентов. Большие разделы должны иметь достаточно воздуха, но не превращайте рабочую CRM в лендинг с чрезмерными пустыми областями.

- Содержимое карточки должно иметь последовательные внутренние отступы.
- Группируйте связанные показатели вместе.
- Между группами используйте пространство, фон или разделитель — в зависимости от визуального уровня.
- Не заключайте каждую подпись или каждое число в отдельную карточку без функциональной причины.
- Учитывайте длинные имена, локализованные подписи и большие денежные суммы: содержимое не должно ломать ширину контейнера.

### Тени и границы

Тени — мягкие и сдержанные. Используйте их для поднятых поверхностей и плавающих элементов, а не для каждой строки.

В карточных списках на мобильных предпочтительны общая поверхность и тонкие разделители строк, а не стопка самостоятельных карточек с одинаковыми тенями.

## 6. Кнопки, формы и интерактивные состояния

### Кнопки

Используйте `Button` из `app/components/ui/button.tsx`, а не создавайте свои классы кнопки с нуля.

Семантика вариантов:

- `default` — главное действие текущего контекста.
- `secondary` — вторичное действие с акцентной заливкой.
- `outline` — нейтральное действие.
- `ghost` — ненавязчивое вспомогательное действие.
- `destructive` — удаление или другое опасное действие.
- `glass` — небольшие плавающие контролы, которым нужна стеклянная поверхность.
- `link` — действие, визуально представленное ссылкой.

Не размещайте рядом несколько одинаково ярких primary-кнопок, если действия различаются по важности. Для асинхронных операций подключайте встроенный prop `loading`, чтобы состояние было заметно и повторный submit блокировался.

### Размеры для touch

На мобильных кнопки стандартного размера обычно имеют высоту 48 px, крупные — 52 px; иконки-кнопки обычно не меньше 44 px. Не уменьшайте интерактивную область ради визуальной компактности. Если сама иконка небольшая, кликабельная область всё равно должна быть достаточной.

### Поля и формы

- Переиспользуйте компоненты из `app/components/ui/form/`.
- Подписывайте поля явно; одного placeholder недостаточно.
- Сохраняйте видимые состояния фокуса, ошибки и disabled.
- Ошибки располагайте рядом с соответствующим полем и формулируйте конкретно.
- Предотвращайте повторную отправку во время загрузки.
- На узких экранах формы должны помещаться в ширину viewport без горизонтального скролла.

## 7. Навигация и адаптивная компоновка

### Десктоп

Основная компоновка состоит из бокового меню, верхнего Header и прокручиваемой рабочей области.

- Используйте общий Sidebar и конфигурацию навигации, а не добавляйте локальные независимые пункты меню.
- Активный пункт должен быть понятен без наведения.
- Не допускайте, чтобы широкие таблицы перекрывали меню или важные элементы управления.
- По возможности сохраняйте общую структуру и ритм между страницами.

### Мобильные устройства

Ниже точки `md` основная навигация предоставляется компонентом `BottomNav`. Это не уменьшенная копия Sidebar.

- Основные разделы находятся в плавающей нижней капсуле; центральная кнопка `+` предназначена для основного сценария создания операции, если он доступен пользователю.
- Второстепенные пункты находятся в панели «Ещё».
- На формах создания/редактирования и при открытой экранной клавиатуре нижняя навигация скрывается.
- Учитывайте `env(safe-area-inset-top)` и `env(safe-area-inset-bottom)`.
- Основное содержимое должно иметь нижний отступ, достаточный для прокрутки за плавающей навигацией.
- Используйте карточки/строки вместо сжатия всех десктопных колонок в узкий экран.
- Учитывайте длинные локализованные строки, системное увеличение текста и маленькую ширину экрана.

В проекте используется адаптивный подход Tailwind; точку `md` считайте основным переходом между мобильной и десктопной оболочками, но отдельные компоненты могут иметь свои брейкпоинты.

## 8. Таблицы, списки и фильтры

Страницы сущностей должны по возможности использовать общие шаблоны списков.

### Десктопные таблицы

- Заголовки столбцов должны быть читаемыми и иметь ясную связь с содержимым.
- Денежные и количественные значения должны быть визуально выровнены.
- Последний столбец действий должен оставаться доступным при горизонтальном скролле там, где для этого включён `pinLastColumn`.
- Большое число полей можно сделать необязательными через `ColumnToggle`, вместо того чтобы перегружать стартовое представление.
- Загрузка, ошибка, пустой результат и офлайн-отсутствие кеша должны иметь разные, понятные состояния.

### Мобильные списки

- Не пытайтесь показать все столбцы настольной таблицы на мобильном экране.
- Выносите главную информацию в сущностную карточку: название, важный статус, ключевое число и доступные действия.
- Используйте общий блок с разделителями, когда строки относятся к одной коллекции.
- Всю строку можно делать переходом к деталям, но кнопки действий внутри неё должны оставаться отдельными, доступными целями нажатия.

### Фильтрация

- Используйте общий `FilterSheet` и типизированные конфигурации фильтров.
- Отображайте число активных фильтров и давайте простой способ сбросить их.
- Поиск должен оставаться понятным и удобным для быстрого доступа.
- На узких экранах кнопки панели инструментов должны переноситься, а не сжиматься и не перекрывать друг друга.

## 9. Дашборд и аналитические данные

Дашборд должен помогать принимать решения, а не просто отображать графики.

Экран владельца (`/dashboard`, вкладка «Обзор») отвечает на вечерние вопросы лавочника: сколько продано, сколько денег получено, кто должен, что заканчивается, что идёт лучше или хуже, что требует внимания. Он написан для нетехнического человека на телефоне, а не как панель метрик.

Иерархия:

1. Заголовок, период и фильтр продавца.
2. «Продано» — одна крупная цифра и две строки под ней: «Получено деньгами» и «Отдано в долг». Это разные понятия, их нельзя сливать в один «доход».
3. «Что требует внимания» — только критичные и предупреждающие рекомендации, каждая строка — ссылка на нужный список.
4. «Нам должны» (долги на сейчас) и «Что заканчивается» (остатки по продажам за фиксированные 28 дней).
5. Лучшие товары, категории, которые стали продаваться заметно лучше или хуже, график по дням, способы оплаты, подробности и последние операции.

Вкладка «Склад» (`/dashboard/inventory`) устроена по тем же правилам: «Что заказать» (до 10 самых срочных, с пометкой, если их больше), «Состояние склада» (стоимость по цене продажи и только непустые состояния — каждое ссылка на список), «Что возвращают». Она читает тот же запрос, что и карточка склада на «Обзоре» (`useStockOverview`), поэтому фильтры периода и продавца на ней скрыты: они ничего не меняют, а кнопки, которые ничего не делают, подрывают доверие к тем, что работают.

Правила содержания:

- Показываем только то, что подтверждено данными. Если данных мало (период короче `MIN_DAYS_FOR_TREND`, нет продаж, нет сохранённой копии офлайн), экран прямо об этом говорит и не рисует процентов, трендов и «падений».
- Рекомендация состоит из статуса, короткого объяснения и действия, но только там, где за ней есть расчёт. Кнопок вроде «Добавить в закупку» нет, пока нет самой функции.
- Сравнение товаров с прошлым периодом бэкенд не отдаёт, поэтому «лучше или хуже» сравнивает только категории.
- Пороги и размеры списков для этого экрана лежат в `app/config/dashboard.ts`.
- `MetricCard` остаётся для KPI со сравнением периодов на других экранах; обзор владельца его больше не использует. Обычные `StatCard` — для простых показателей.
- Графики должны использовать токены `--chart-1` … `--chart-5`, а подписи и подсказки — переводы текущего языка.
- Значимые показатели должны по возможности вести к релевантному списку с уже применённым фильтром.
- Не показывайте цветную дельту без объяснимого смысла: для возвратов, долгов и расходов направление «выше» не всегда означает «лучше».
- Пустые аналитические наборы должны иметь осмысленное состояние, а не сломанную или пустую диаграмму.

## 10. Liquid Glass и декоративные эффекты

В проекте есть два разных уровня стеклянного оформления:

- `liquid-glass` — более выраженная поверхность для плавающих элементов, прежде всего нижней мобильной навигации и выдвижной панели.
- `glass-control` / `variant="glass"` — более лёгкий вариант для небольших управляющих кнопок.

Эти классы используют полупрозрачные градиенты, `backdrop-filter`, блики и отдельные настройки для тёмной темы.

Правила:

- Не превращайте все карточки и панели в стеклянные поверхности.
- Не используйте стекло за мелким текстом, если фон делает его труднее читать.
- Для важных действий предпочитайте ясные состояния и контраст, а не прозрачность.
- Сохраняйте fallback для браузеров без поддержки размытия и вариант с уменьшенной прозрачностью.
- Перед добавлением новых blur-слоёв проверяйте производительность на Android WebView и недорогих устройствах.

## 11. Анимации и обратная связь

Используйте `motion/react` и существующие компоненты анимации, если это соответствует сценарию.

Хорошие сценарии: мягкое появление экрана, перемещение активного индикатора, появление списка, обновление показателей и явная индикация загрузки.

Не анимируйте каждый элемент независимо без необходимости. Анимация должна быть короткой, предсказуемой и помогать понимать состояние интерфейса.

Обязательно:

- уважайте системную настройку `prefers-reduced-motion`;
- не блокируйте взаимодействие длительными переходами;
- не полагайтесь только на анимацию для сообщения об успехе или ошибке;
- проверяйте переходы на реальных мобильных устройствах.

Для hover-состояний не предполагайте наличие мыши: на touch-устройствах не должно оставаться «залипших» hover-эффектов. Предоставляйте явную обратную связь при нажатии и фокусе.

## 12. Тёмная тема

Тема управляется через существующий ThemeProvider / `next-themes`. Не реализуйте отдельный независимый переключатель темы для одной страницы.

При добавлении UI проверяйте обе темы:

- фон страницы, карточки, popover и sidebar;
- границы, разделители и тени;
- текст, placeholder, иконки и disabled-состояния;
- статусы и графики;
- стеклянные поверхности и их fallback;
- фокус и контраст интерактивных элементов.

Избегайте жёстко заданных `bg-white`, `text-black` и прямых hex-значений там, где элемент должен адаптироваться к теме. Исключения допустимы для фирменного логотипа или конкретного брендового ассета, где фиксированные цвета являются частью самого изображения.

## 13. Локализация и контент

Приложение поддерживает русский, английский и таджикский языки.

- Пользовательские строки должны находиться в locale-файлах `public/locales/`, а не быть захардкожены в JSX.
- Не закладывайте фиксированную ширину под строку только на русском языке.
- Проверяйте кнопки, вкладки, названия статусов, заголовки таблиц и мобильную навигацию после смены языка.
- Не обрезайте критически важные названия и суммы без необходимости.
- Даты и денежные значения форматируйте через существующие функции проекта.

## 14. Доступность и контрастность

Визуальная красота не должна снижать доступность.

- Обычный текст должен стремиться к контрастности **не менее 4.5:1**, крупный текст — не менее **3:1** по WCAG AA.
- Для фокуса клавиатуры нужен различимый `focus-visible`-индикатор.
- Интерактивные иконки должны иметь доступное имя (`aria-label`), если их смысл не описан видимым текстом.
- Не обозначайте статус одним цветом: добавляйте текст, число или иконку.
- Кнопка должна выглядеть как действие, ссылка — как переход, а некликабельная плитка не должна получать hover-эффект, обещающий клик.
- Учитывайте touch-цели, системные safe areas, увеличение текста и reduced motion/transparency.

**Особое внимание:** текущие синие и семантические цвета нужно проверять в контексте конкретного текста и фона. Например, белый текст на основном синем `#007AFF` имеет контраст примерно 4.0:1, то есть не достигает порога 4.5:1 для обычного текста. Если это комбинация для кнопки с обычным текстом, проверьте более контрастный оттенок или другой способ сочетания текста и заливки, не меняя фирменный акцент без необходимости.

## 15. Состояния интерфейса

Для каждой страницы/компонента, работающего с данными, подумайте о следующих состояниях:

- **Загрузка:** skeleton или понятный индикатор, сохраняющий примерный размер будущего содержимого.
- **Успех:** понятная обратная связь, без чрезмерного декоративного эффекта.
- **Ошибка:** доступное объяснение и действие для восстановления, если оно возможно.
- **Нет данных:** контекстное пустое состояние, отличающееся от ошибки.
- **Офлайн:** честное объяснение, какие данные доступны и какие действия ожидают синхронизации.
- **Опасное действие:** подтверждение через существующий `ConfirmDialog`.
- **Нет разрешения:** не показывать пользователю действия, которыми он не может воспользоваться.

Не заменяйте ошибки пустыми карточками, а отсутствие данных — бесконечным skeleton.

## 17. Запрещённые паттерны и анти-паттерны

Без обоснованной необходимости не следует:

- добавлять новую палитру или новый шрифт только для одной страницы;
- вводить другой радиус карточек без проверки существующих компонентов;
- создавать локальную копию `Button`, `DataTable`, `Panel`, `StatCard` или общего toolbar;
- использовать стеклянные поверхности и сильные тени на каждом блоке;
- применять hover как единственный способ показать интерактивность;
- помещать все данные в мобильную таблицу с горизонтальным скроллом, если их можно представить карточками;
- жёстко задавать ширину текстовых элементов так, чтобы переводы ломали layout;
- использовать цвет как единственный индикатор статуса;
- уменьшать кликабельную область ради более компактного вида;
- добавлять анимацию, которая не сообщает о смене состояния;
- оставлять кнопки без реального действия или выдавать недоступную функцию за работающую;
- использовать прямые hex-цвета и фиксированные светлые поверхности там, где требуется поддержка dark mode.

## 18. Чек-лист перед завершением UI-изменения

- [ ] Использованы существующие компоненты и семантические токены.
- [ ] Проверены светлая и тёмная темы.
- [ ] Проверены мобильный и десктопный layout.
- [ ] Не появляется горизонтальный скролл страницы на узком viewport.
- [ ] Длинные русские и таджикские строки не ломают интерфейс.
- [ ] Загрузка, ошибка, пустое и офлайн-состояния выглядят корректно.
- [ ] Фокус клавиатуры видим, touch-цели достаточно большие.
- [ ] Контрастность важного текста и статусов проверена.
- [ ] Hover не является единственным способом обратной связи.
- [ ] Анимации уважают `prefers-reduced-motion`.
- [ ] Стеклянные эффекты имеют читаемый fallback и не мешают содержимому.
- [ ] Проверены важные бизнес-сценарии: создание, редактирование, поиск, фильтры и опасные действия.
- [ ] Выполнены `npm run typecheck` и `npm run build`, когда изменение затрагивает код приложения.

---

**Главное правило:** новый UI TradeCRM должен выглядеть как часть уже существующего продукта, а не как отдельный шаблон. Сначала соблюдайте дизайн-токены и общие компоненты, затем добавляйте только те исключения, которые действительно нужны конкретному сценарию.
